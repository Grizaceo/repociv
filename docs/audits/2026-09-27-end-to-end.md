## 0. Veredicto

**El gate está 100% verde y la maquinaria de seguridad del servidor es genuinamente buena** —
pero hay **una regresión de seguridad activa en esta máquina**: el dev server de Vite está
escuchando en `0.0.0.0` e incrusta el token del bridge en el JavaScript que sirve. Cualquier
host de la LAN puede leer ese token y ejecutar agentes. No requiere `REPOCIV_REMOTE`.

El resto son riesgos altos de **divergencia dev/prod** y deuda de mantenimiento, no de seguridad.

**Prioridad única:** revertir `vite.config.ts:50` a `host: '127.0.0.1'`.

## 2. BLOQUEANTE — Token del bridge filtrado a la LAN

**Severidad: CRÍTICA · explotable HOY, sin `REPOCIV_REMOTE` · red: LAN/Tailnet/Wi-Fi compartido**

`vite.config.ts:44-71` hace dos cosas que se contradicen con la intención documentada:

```ts
server: {
  // Loopback-only: la UI de RepoCiv no se expone al tailnet/WSL-LAN.   ← comentario
  // El bind 0.0.0.0 previo era la misma exposicion que el gateway (:8742).
  // Se accede via 127.0.0.1:5273 / localhost:5273.
  host: '0.0.0.0', // loopback-only was hiding the server from Windows browser  ← realidad
  // allowedHosts:true se mantiene inofensivo porque el bind ya es loopback
  // (solo acepta conexiones que lleguen a 127.0.0.1); no es vector de exposicion.
  allowedHosts: true,
  proxy: { '/bridge': { target: `http://localhost:${BRIDGE_PORT}`, ws: true, ... } },
}
```

Y `vite.config.ts:30-43` incrusta el token **del lado servidor** en el bundle cliente:

```ts
const repocivToken = env.VITE_REPOCIV_TOKEN ?? env.REPOCIV_TOKEN ?? '';
define: {
  ...(repocivToken && !env.VITE_REPOCIV_TOKEN
    ? { 'import.meta.env.VITE_REPOCIV_TOKEN': JSON.stringify(repocivToken) } : {}),
```

**Verificado en el `.env` vivo (sin imprimir ningún valor):** `REPOCIV_TOKEN` presente con
**64 chars** (mínimo exigido: 32), `VITE_REPOCIV_TOKEN` **ausente** → la cadena de fallback
**se activa**, `REPOCIV_REMOTE` **no configurado**. El bridge está correctamente en
`127.0.0.1` (`bridge.py:97`) — la superficie expuesta es el **proxy**, no el bind.

**Explotación:** desde cualquier peer de la LAN, `GET http://<ip-lan>:5273/src/bridgeEnv.ts`
devuelve el token; después `POST http://<ip-lan>:5273/bridge/commands` con
`X-RepoCiv-Token` ejecuta `claude --print --dangerously-skip-permissions`
(`agent_runner.py:1092`) como el usuario. `allowedHosts: true` además elimina la protección
de DNS-rebinding de Vite.

### Es una regresión accidental, no una decisión

`git blame` da la cadena causal completa:

| Fecha | Commit | Cambio |
|---|---|---|
| 2026-08-13 | `610ce8f9` | se añade `allowedHosts: true` |
| 2026-08-23 | `b63def97` | **endurecimiento**: bind a `127.0.0.1` + comentarios "loopback-only" |
| 2026-09-07 | `e6c3d2a2` | `test(coverage): widen the coverage exclude…` — revierte el bind a `0.0.0.0` |

El diff de `e6c3d2a2` es literalmente una línea, en un commit cuyo mensaje no tiene nada que
ver con networking:

```diff
-      host: '127.0.0.1',
+      host: '0.0.0.0', // loopback-only was hiding the server from Windows browser
```

Los comentarios del 2026-08-23 quedaron ahí, **afirmando una premisa que ya es falsa** — por
eso sobrevivió 3 semanas. Arreglar el bind **y** los comentarios, o el próximo toque lo rompe de nuevo.

**Fix:** `host: '127.0.0.1'` + `allowedHosts: false` + corregir los comentarios de las líneas 47-52.
Si hace falta exponer en LAN para WSL/Windows, hacerlo con `REPOCIV_REMOTE` + token, nunca con el
dev server por defecto.

## 3. ALTA — La API de dev no es la API de producción

**Severidad: ALTA (corrección) · red: LAN (el plugin no valida token)**

`vite-plugins/repociv.ts` (889 líneas) sirve `/api/*` **solo desde `configureServer`**
(línea 882) → es **dev-only**. El bridge Python sirve un conjunto distinto. Mismas URLs,
código y comportamientos distintos.

### 3.1 Seis endpoints existen únicamente en dev

El frontend los llama, pero **no existen en el servidor** (verificado: 0 coincidencias en
código no-test de `server/`):

| Endpoint | Python | Plugin | Llamado desde |
|---|---|---|---|
| `/api/git/:name` | **ausente** | ✅ | `ui/chat/panel.ts:94`, `ui/city.ts:119`, `ui/localSpatialPreview.ts:293` |
| `/api/skill-health/:name` | **ausente** | ✅ | `map.ts:268` |
| `/api/session-tint/:name` | **ausente** | ✅ | `map.ts:281` |
| `/api/repo/pick` | **ausente** | ✅ | `ui/constructionPanel.ts:88` |
| `/api/repo/inspect` | **ausente** | ✅ | `ui/constructionPanel.ts:95` |
| `/api/repos/refresh` | **ausente** | ✅ | sin caller |

`playwright.config.ts:49` arranca **solo** `npm run dev` → **toda la suite e2e corre contra la
API de dev. Nada en el repo ejercita la forma de la API de producción.**

### 3.2 Cinco divergencias semánticas TS ↔ Python

`vite-plugins/repoRootsState.ts` (188 líneas) vs `server/repo_roots_state.py` (333 líneas):

| # | Comportamiento | TS (dev) | Python (prod) |
|---|---|---|---|
| a | `addRepoSelection` cambia el root activo | sí, siempre (`repoRootsState.ts:125`) | no (`repo_roots_state.py:214-218`) |
| b | remove borra de | todos los roots (`:180`) | solo el activo, + actualiza `lastSeen` |
| c | root sucesor tras eliminar | orden de inserción (`repociv.ts:665`) | `sorted()` (`repo_roots_state.py:156`) |
| d | `decode_repo_id` expande `~` | no (`:60`) | sí (`repo_roots_state.py:260`) |
| e | **el repo debe estar en la selección** | **no** | **sí** + containment |

**3.2e es un problema de seguridad**, no solo de consistencia: el plugin acepta cualquier ruta
absoluta sin verificación de pertenencia —

```ts
// vite-plugins/repociv.ts:329-333
if (decodedRaw.startsWith('/') || decodedRaw.startsWith('~')) {
  const direct = resolve(expandUser(decodedRaw));
  if (repoExists(direct)) return direct;
```

— y **no hace ninguna comprobación de token** (0 coincidencias de `token|auth` en
`repociv.ts`). Combinado con el bind `0.0.0.0` de F1, la API de dev sin auth es alcanzable
desde la LAN.

**Fix:** convertir el plugin en un *shim* fino que proxee `/api/*` no implementado a
`BRIDGE_PORT`; o borrar las rutas duplicadas. Mínimo: un test de conformidad que corra las
mismas expectativas contra ambas implementaciones.

## 4. MEDIA — Hallazgos verificados

**F4 — `vite-plugins/` nunca se typechequea.** `tsconfig.json:22` es `"include": ["src"]`.
`npm run build` es `tsc && vite build`, así que **1.441 líneas no-test de `vite-plugins/` +
188 de `vite.config.ts` quedan fuera de todo chequeo de tipos**. El Vite config que causa F1
nunca fue typechequeado. *Fix: `include: ["src", "vite-plugins", "vite.config.ts"]` — PR propio.*

**F5 — Fuga real en `gacetaWidget` (verificada).** `src/ui/gacetaWidget.ts`:
`mountGacetaWidget` (`:37`) no tiene guarda de idempotencia, registra
`window.addEventListener('repociv:city-selected', …)` con handler anónimo (línea 106) que
`unmountGacetaWidget` (`:118`) **nunca quita**, y hace
`_refreshTimer = setInterval(...)` (`:114`) **sin limpiar el handle previo**. Se llama desde
`main.ts:425` y desde `capitalPanel.ts:165` en **cada apertura del panel de capital**
(`renderer.ts:17`). → un `setInterval` huérfano permanente + un listener por apertura.
*Fix: guarda de montaje + `clearInterval` antes de reasignar + handler nombrado con
`removeEventListener`.*

**F6 — `/api/claude-live/spawn` sin containment.** `server/routes/core.py` pasa el `cwd` del
caller directo a `claude_live.get_manager().spawn(cwd)`; `server/claude_live.py:121-146` solo
valida `os.path.isdir` y lanza con `--dangerously-skip-permissions`. No hay
`resolve_selected_repo` como sí lo hay en `POST /commands` (`routes/core.py:953-972`) y en
`run_agent` (`agent_runner.py:355-368`). Cualquier directorio existente (`/etc`, `~/.ssh`)
es aceptado. *Requiere token válido.*

**F7 — El path WebSocket salta los rate limiters.** `bridge.py:1314-1316` valida el comando
pero no el target y no aplica limiter; `routes/core.py:989-999` sí aplica
`_endpoint_rate_limiter` + `_agent_rate_limiter`. *La contención NO se evade*
(`run_agent` revalida), lo que se pierde es el tope de recursos. Nada testea que el path WS
aplique `_validate_command_target`.

**F8 — SSRF almacenado vía manifiesto de wonder.** `routes/wonder_ops.py:107-122` persiste
el manifiesto del caller verbatim, incluido `health.url`;
`wonder_registry.py:242-244` la dereferencia con `urllib.request.urlopen` en un GET. Sin
allowlist de esquema/host ni bloqueo de IP privada. *(El `id` sí está saneado — no hay traversal.)*

**F9 — Los timeouts de subprocess son inalcanzables en 4 de 5 spawns.**
`agent_runner.py:1017` (hermes), `:1092` (claude-code), `:1246` (cursor), `:1287` (openclaw)
hacen `for line in proc.stdout:` — **bloquean hasta EOF antes de alcanzar** el
`proc.wait(timeout=600)`. Un hijo que nunca cierra stdout retiene el hilo para siempre. El
path de codex sí es correcto (`communicate(timeout=600)`, `:1353`). Tampoco hay
`start_new_session=True` (comparar `wonder_launcher.py:674`), así que los agentes quedan
huérfanos si el bridge muere.

**F10 — El log "a prueba de manipulación" se firma con clave pública hardcodeada.**
`security_harness.py:374`: `_HMAC_KEY = os.environ.get("REPOCIV_HMAC_KEY", "repociv-audit-default-key")`.
El docstring de la clase (`:382`) promete "HMAC tag for tamper evidence". Con la clave por
defecto —que está en el repo— cualquiera forja entradas que validan. No avisa cuando
`REPOCIV_HMAC_KEY` no está seteado.

**F11 — `terminalPanel.ts` es un stub que mantiene deps muertas.** 32 líneas,
`write(_text: string): void {}` **descarta todo**, **cero imports de xterm**. Sin embargo
`@xterm/xterm` + `@xterm/addon-fit` son dependencias de producción (`package.json:46-47`),
`vite.config.ts:165-167` reserva un chunk `vendor-terminal` que nunca se emite, y `knip.json:6-9`
suprime el reporte para poder conservarlas. El hotkey `t` (`hudWiring/hotkeys.ts:306`) hace
tracking y toggle de un booleano. *Fix: borrarlo todo, o implementarlo.*

**F12 — `requirements.lock` nunca se instala; `mypy` nunca se ejecuta.**

- `ci.yml:44` instala `requirements.txt` (rangos abiertos), **no** `requirements.lock`.
  `cache-dependency-path: requirements.lock` solo afecta la **clave de caché** — el lock es
  decorativo. CI instala versiones flotantes de ~10 paquetes. El comentario de `ci.yml:41-42`
  ("ruff is pinned in requirements.txt — single source of truth") agrava la confusión.
- `mypy` está en la `[tool.mypy]` de `pyproject.toml` con un bloque de 12 líneas sobre un
  "ratchet toward blocking", y `scripts/check.sh:146-153` tiene el paso — pero mypy **no está**
  en `requirements.txt` ni en `requirements.lock` ni en `.venv`. El paso nunca se ejecuta.
  Un gate de calidad documentado que es estructuralmente inerte.

## 6. Lo que está MUY bien (no tocar)

La revisora de seguridad verificó empíricamente, no por lectura:

- **Auth centralizada** al tope del handler; `hmac.compare_digest` (constante); sin
  `do_PUT`/`DELETE`/`PATCH`; `enforce_token_policy` **rechaza arrancar** con bind no-loopback
  sin token; `remote-start.sh` exige ≥32 chars por separado.
- **La cola de approvals no se puede degradar.** `validate_command` *permite* que el caller
  supplyee `risk`, pero `_TYPE_POLICY` (keyed on `cmd.type`) lo sobreescribe, y el floor solo
  **promociona**. Probado ejecutando: `git_commit risk=low → approve`, `evil_type → blocked`.
  MCP usa exactamente el mismo gate.
- **Containment de rutas real** (realpath + `commonpath`), con re-chequeo de symlinks en
  `get_repo_file_tree` y allowlist de slug en assets. **Ningún traversal encontrado.**
- **Cero `shell=True`** en ~40 sitios de subprocess; **todo YAML por `safe_load`**; sin
  `pickle`/`eval`/`marshal` fuera de tests.
- **Higiene de secretos**: ni `.env` ni `bridge.log` trackeados; ningún endpoint devuelve
  secretos; `redact_env_for_spawn` quita `*_TOKEN` del env de los agentes hijos.
- **Tipos excellentemente disciplinados**: 1 `as any` en todo `src/` no-test, 0 `@ts-ignore`,
  0 `@ts-nocheck`, 0 `catch` vacíos en 175 sitios, `strict` + `noUncheckedIndexedAccess` on.
- **Higiene de repo impecable**: `.gitignore` cubre todo el artefactos; 0 archivos de build
  trackeados; budgets de assets y de bundle aplicados en CI.
